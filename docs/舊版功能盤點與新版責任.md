> 性質：**以程式碼為準的功能盤點與架構決策輸入**，不是「新版已實作」清單，也不是正式遊戲伺服器驗收。\

## 一、盤點方法與可信度

1. 分別取得兩個舊專案最新 `main` 的完整 Git tree，確認檔案確實存在；讀取 README、桌面 `docs/MODULARIZATION_PLAN.md`、Android `ANDROID/FEATURE_PARITY.md`、`android_app/dashboard.py`、`android_app/features.py` 及資源管理原始碼。
2. **確認存在**：程式或頁面入口確有對應責任；只代表「有原始碼」，不代表已通過正式伺服器 E2E、每一項操作都允許啟動，或新版已具備。
3. **條件式／受限**：舊版程式、文件明確包含保守拒絕、唯讀或未驗證操作；新版必須原樣保留安全限制，不能因模組重寫就放行。
4. **待驗證**：功能所需的精確官方 AssetPath、版本、資料表欄位、相依 Bundle、網路封包或跨平台行為尚無完整對照。不得由檔名、分類標籤直接產生下載／操作權限。
5. 證據範圍是檔案及代表性實作／測試，非逐行完整呼叫圖。真正遷移某功能前，還需追蹤 import／呼叫者／命令與 State 讀寫路徑。

## 三、舊版 Android 實際入口與平台差異

- Android `android_app/dashboard.py` 有 15 個角色功能頁：角色概況、包包與特技、小地圖、戰場陣形、聊天、組隊、夥伴出戰、遠征、副本資料、角色能力、煉金、製作、經驗效率、事件紀錄、AI 與補給設定。
- `android_app/features.py` 的 `GAME_COMMANDS` 是可經 IPC 傳送的操作白名單；`STATE_FIELDS` 是可投影的狀態欄位。**頁面存在、命令名稱出現、實際可操作與正式服驗收是不同層級**。
- `android_app/pages/` 包含 `map.py`、`resources.py`、`companions.py`、`expedition.py`、`instances.py`、`production.py`、`social.py`、`attributes.py`、`settings.py` 等，對應觸控友善的 UI 責任。
- `android_app/service.py`、`sessions.py`、`runtime.py`、`java/org/lala/client/ConnectionService.java`、`FloatingOverlay.java`、`vault.py` 是 Android 前景服務、多帳號、懸浮窗、憑證／安全的參考，**不複製舊 Kivy 或 Python-for-Android 實作**。
- 舊 Android `ANDROID/FEATURE_PARITY.md` 的歷史條目有不同日期的實作進度；較新的「2026-10-21 非 NPC 同步」說明桌面部分副本／協力／配點已同步，但 **NPC 對話／互動／商店／新 NPC 索引並未移植 Android**。新版 Android 不得宣稱與桌面完全功能等價。
- 新版 Rust 核心跨平台共用**功能識別、資料驗證、權限與狀態機**；桌面改用 Tauri，Android 改用 Kotlin + Jetpack Compose/FFI。Android 背景服務、流量／電池、私有目錄和密鑰管理屬平台適配。

## 四、責任劃分與開發先後

```text
Rust 共用核心
  ├─ net/protocol/session/state     ← P2：網路、封包、登入、權威狀態
  ├─ resources                     ← P1：官方版本、Manifest、Bundle、快取
  ├─ feature_registry              ← P1 前置：功能識別、啟用、依賴與權限
  ├─ resource_resolver             ← P1：功能→官方資產→依賴封包
  ├─ reservations/commands         ← P2/P5：副作用、材料保留與不確定鎖
  └─ features                      ← P5：帳號、地圖、戰鬥、物品、遠征等
平台 UI
  ├─ desktop (Tauri)               ← P3：功能頁、進度、手動確認
  └─ android (Kotlin/Compose)      ← P4：觸控、工作服務、權限
```

**這是責任示意而非已存在的實際目錄**。新增模組前檢查 Rust Workspace 現有 `resource-manager`、`core-observability`、`feature_resources.rs` 及 `update_plan.rs`，不重複建立相同責任。

工作優先序：

1. **P1 前置盤點（本文件）**：明確列出 LaLa 功能、對應舊程式與測試、功能是否需要靜態素材。
2. **功能需求契約**：每個功能標記「純伺服器／本機／需官方素材／尚未確認」，精確綁定前一律不得發起未知下載。純伺服器操作需明確宣告無素材依賴。
3. **官方資產定位與 P1 驗證**：以官方經驗證 `AssetPath`／`Address` 精確識別資產，展開 Bundle 相依，先計算必要檔數與下載位元組數，再按需取得。
4. **P2 之後逐功能實作**：保留協定與安全拒絕限制；P3、P4 分別接實際應用 UI；不得為了完成 P1 假造功能呼叫事件。
5. **每一功能逐一驗收**：資產清單、缺少／變更、重用／損毀／離線、資源解析、使用該資產的功能狀態、伺服器與實機驗收分別報告。

## 五、尚待逐項解析的風險

- **當前 Rust `feature_resources::Feature` 只列 Account／Map／Battle／Inventory／Expedition／Social／Pet 七種，尚未涵蓋製作、煉金、協力、副本、傳點、NPC、帳篷等舊版實際功能。** 應先確立穩定功能 ID，避免名稱拆分後快取混淆；不可直接視為已完成完整功能註冊表。
- 舊版 `feature_resource_index.py` 只是唯讀診斷，不授權操作；其精確表格對應需獨立核對官方版本及相依 Bundle。舊 `resource_classification.py` 的分類包含檔名規則，**分類不等於功能必要性或下載許可**。
- `docs/MODULARIZATION_PLAN.md` 列明 `smallmaps.zip`、`navigation_data.zip` 等歷史靜態資料尚未證明有等價 1275 官方來源，**不能將其全部宣稱可由官方即時取得**。新版只允許官方指定來源，沒有等價資料時應標示缺口並調整功能呈現。
- 舊版桌面採由官方 `.version`、`.bytes`、`.hash` 組成並驗證 YooAsset Manifest，**不依賴 `.json`／`.report`**。新版目前部分 P1 流程使用 JSON；須先比較來源信任／格式限制，再修正正式路徑，不能將兩者視為完全相同。
- 官方索引的 MD5／CRC32、下載成功、解包成功、遊戲協定可操作是四種不同的驗收證據；任何一項成功都不能自動推論後面成功。
- `wlre/resources/` 舊版內建之檔案並不自動滿足新版「官方單一資源來源」政策，且官方素材不能再散布到 GitHub；不得為了補全功能而複製舊版遊戲素材。
